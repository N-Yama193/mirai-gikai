# Phase 3-② AI要約機能 DB連携 設計仕様

対象: みらい議会Fork版（広川町議会）
前提: Phase 3-①（議案一覧・詳細）完了・コミット済み（7f2001f, origin/develop）

## 1. 概要

一般質問・議案の登録/更新時にAI要約を自動生成し、担当者の確認・承認を経て住民向けページに公開する「自動生成＋手動承認」方式を採用する。

## 2. 生成トリガー方式

- 一般質問・議案の登録/更新をトリガーに、**非同期**でAI要約を生成する（保存処理をブロックしない）。
- 生成結果はステータス `draft` として保存し、この時点では住民向けページには表示しない。
- 管理画面で担当者が内容を確認し、「公開」操作を行うとステータスが `published` に変わり、住民向けページに反映される。
- 本文が一定以上変更された場合のみ自動再生成する（軽微な修正での無駄な再生成・再課金を避ける）。差分検知は本文のハッシュ値で行う。
- 既に `published` の要約は自動上書きしない。本文変更時は新しい下書きを別途生成し、担当者に再確認を促す。

## 3. DBスキーマ変更

一般質問テーブル・議案テーブルそれぞれに以下のカラムを追加（1対1関係のため別テーブル化はしない）。

| カラム名 | 型 | 説明 |
|---|---|---|
| `ai_summary` | text/json | 生成された要約（points, conclusionを含むJSON） |
| `ai_summary_status` | enum | `none` / `draft` / `published` |
| `ai_summary_generated_at` | datetime | 生成日時 |
| `ai_summary_published_at` | datetime | 公開日時 |
| `ai_summary_source_hash` | string | 生成元本文のハッシュ値（再生成判定用） |

## 4. 使用AI

Claude API を使用する。

## 5. プロンプト設計

### 設計方針

質問者名・提出者・議決結果など、登録時点で既にDBに存在する情報はAIに抽出させない。AIには本文からの論点・結論の要約のみを担当させ、ハルシネーション（存在しない人名・事実の捏造）のリスクを下げる。表示テンプレート側で既存DBの値とAI生成結果を組み合わせる。

### 5-1. 一般質問用プロンプト

```
あなたは町議会の議事録要約アシスタントです。
以下の一般質問の質疑応答本文を要約してください。

【本文】
{question_body}

以下のJSON形式で出力してください。本文に記載のない内容は推測せず、不明な場合は空文字にしてください。

{
  "points": ["論点1", "論点2", ...],  // 2〜4個程度、各30〜50字程度
  "conclusion": "結論・町の対応方針を100字程度で"
}
```

### 5-2. 議案用プロンプト

```
あなたは町議会の議事録要約アシスタントです。
以下の議案の提案理由・審議内容を要約してください。

【本文】
{agenda_body}

以下のJSON形式で出力してください。本文に記載のない内容は推測せず、不明な場合は空文字にしてください。

{
  "points": ["審議のポイント1", "審議のポイント2", ...],
  "conclusion": "議案の要旨・結論を100字程度で"
}
```

### 5-3. 表示レイアウト（例）

```
質問者：〇〇議員
論点：
・論点1
・論点2
結論：
（conclusion）
```

## 6. 実装時の注意点

- 非同期ジョブ化（キュー/バックグラウンド処理）でAPI呼び出しを保存処理から切り離す。
- API呼び出し失敗時は `ai_summary_status` を `none` のまま保持し、リトライ可能な状態にする。
- 管理画面に「公開」「再生成」ボタンを用意する。
- 公開済み要約が存在する状態で本文が変更された場合、担当者に再確認が必要な旨をUI上で明示する。
